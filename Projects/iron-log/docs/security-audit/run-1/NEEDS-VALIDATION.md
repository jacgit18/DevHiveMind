# Needs validation

Prioritized leads without severity. Each is blocked on a fact that source and the offline sandbox cannot show. Nothing here is live-test guidance; the owner checks are read-only observations.

## 1. Anonymous unbounded request body on the better-auth mount may exhaust memory on the single 512Mi Cloud Run instance

- **Fingerprint:** `auth-mount-unbounded-request-body`
- **Claimed root cause:** app.all('/api/auth/*splat', toNodeHandler(auth)) is mounted ahead of the body parsers. There is no pre-handler Content-Length or byte cap, and the better-auth adapter sets no bodySizeLimit. The better-call router awaits getBody(request), which buffers the full body. The other parsed routes are capped (4kb, 4mb and 100kb) but this mount is not.
- **Description:** The better-auth handler is mounted at /api/auth/*splat before any express.json parser. The mount has no body-size cap, and better-call buffers the whole request body in memory before the route handler runs. An anonymous client can POST a very large JSON body to an /api/auth route such as /api/auth/sign-in/social. The hunter's local run accepted a 32 MiB body and server RSS rose by about 65 MB. Three concurrent 16 MiB bodies raised RSS by about 77 MB. Memory growth is therefore roughly proportional to body size, about 2x. The production service runs a single instance with 512Mi, concurrency 40 and max-instances 1, so a handful of concurrent large bodies could plausibly cause an out-of-memory restart of the only instance. Restart or OOM behaviour on Cloud Run, and the platform's own request-size cap (about 32 MiB on HTTP/1), cannot be observed from source or locally. Per-IP rate limits count requests rather than bytes, and a client can open 6-10 requests within the 10 per minute sign-in limit, so they do not prevent the burst. No crash was demonstrated, so no stronger result is claimed.
- **Source trace:**
1. `server/app.ts:83` (entrypoint) Anonymous POST to /api/auth/sign-in/* passes originGuard (a missing Origin header is allowed) and a request-count rate limit of 10 per minute per IP. The limit does not consider body bytes.
2. `server/app.ts:85` (propagation) app.all('/api/auth/*splat', toNodeHandler(auth)) is registered before express.json, so no size limit applies and the raw stream goes straight to better-auth.
3. `server/app.ts:91` (propagation) express.json({limit:'100kb'}) is registered after the auth mount, so it never covers /api/auth. This shows the protection exists elsewhere but not here.
4. `node_modules/better-call/dist/router.mjs:67` (sink) body: await getBody(request, allowedMediaTypes) reads and parses the entire request body into memory with no size cap, so heap and RSS grow with the attacker-chosen body size.
- **Verified evidence:**
  - `server/app.ts:85` I re-read the mount. It has no body cap and sits before every body parser, and the comment says better-auth reads the body itself.
  - `server/app.ts:44` AUTH_LIMITS is {signIn:10/min, other:120/min} per IP and counts requests only. Bytes per request are not limited, and a few large requests fit inside the limit.
  - `node_modules/better-call/dist/router.mjs:67` I confirmed that getBody is awaited before middleware and the handler run, with no size check (better-call 1.4.0, better-auth 1.7.7). A grep of server/ for bodyLimit, maxBody or bodySizeLimit found nothing.
  - `scripts/deploy-cloud-run.sh:89` Deploy uses --max-instances 1 --memory 512Mi --concurrency 40 --timeout 120, so one small instance serves all traffic and 40 requests can be in flight at once.
  - `agents/hunt-avail-cloud-w1/artifacts/out/check-1.txt:8` Hunter's sandbox measurement on Node 20 with better-auth's in-memory adapter and only the auth mount (no originGuard): a 32 MiB body returned 200 with a peak RSS delta of +65 MB (line 8). Three concurrent 16 MiB bodies gave +77 MB (line 9). Idle RSS was about 87 MB. I read this artifact and did not re-run it.
- **Blockers:**
  - Whether Cloud Run's front end rejects or buffers oversized requests before the container, and the exact cap (about 32 MiB for HTTP/1), cannot be observed from source or locally.
  - The real OOM threshold and restart behaviour under 512Mi, with the production Node 22 runtime, Neon pool and baseline RSS, is unmeasured. Local numbers (about 2x body size, about 90-150 MB idle) suggest roughly 5-8 concurrent 32 MiB bodies would be needed.
  - It is unknown whether a container restart causes user-visible downtime. min-instances is 0 and max-instances is 1, so the outage depends on cold-start time and on whether queued requests are retried.
- **Bounded local plan:** Non-destructive: run the real server/app.ts createApp with the better-auth in-memory adapter and the Node 22 production Dockerfile image if available. Cap the process heap and memory to 512 MiB (for example a cgroup limit or --max-old-space-size). Send N concurrent 8-32 MiB bodies to POST /api/auth/sign-in/social over a unix socket with no Origin header. Record peak RSS and the N at which the process is killed or returns errors. Then add express.json-style or Content-Length pre-checks on /api/auth and confirm that oversized requests get 413 with no RSS growth.
- **Owner-observed deployment check:** Owner-run on a staging Cloud Run service with the same 512Mi/concurrency-40 config, never production. Send a bounded set of 6-10 concurrent 20-30 MiB POSTs to /api/auth/sign-in/social from one test IP, and watch the Cloud Run memory-utilization and instance-restart metrics and /api/health responses. Also confirm what status Cloud Run returns for a body over 32 MiB.

## 2. Backup bucket soft-delete period is not set, so erased users' dumps may be recoverable past the promised 30 days

- **Fingerprint:** `backup-bucket-soft-delete-outlives-30day-erasure-promise`
- **Claimed root cause:** The bucket-creation and lifecycle configuration in cmd_setup covers only object age. The backup-retention promise in the UI and policy is checked by server/legal.test.ts only against the RETENTION_DAYS constant in the script, so the soft-delete window is not part of the guarantee.
- **Description:** scripts/backup-cloud-run.sh creates the private backup bucket and sets only an age-30 Delete lifecycle rule. It never sets or disables the Cloud Storage soft-delete retention (--soft-delete-duration=0). GCS gives new buckets a default soft-delete window, 7 days for buckets created after the March 2024 change. If that default applies to the live bucket, a dump removed by the lifecycle rule at day 30 stays recoverable for about 7 more days, roughly 37 days after creation. Those dumps hold rows for users who have since erased their data or deleted their account. The in-app notice (DeleteMyData.tsx) and the privacy policy (privacy.html) say backup copies are deleted automatically within 30 days. The mismatch is at most a few days, and the objects are readable only by project principals who hold restore/read rights; the job's service account has objectCreator only. This is a privacy-promise accuracy gap, not an unauthenticated or cross-tenant exposure. The live bucket's soft_delete_policy, and any project-level or organization-level override, cannot be observed from the repository.
- **Source trace:**
1. `src/components/settings/DeleteMyData.tsx:85` (entrypoint) User-facing statement that copies in the nightly backups are deleted automatically within 30 days after the user erases data or deletes the account.
2. `public/privacy.html:94` (propagation) Policy states backups are kept 30 days, then deleted automatically, so erased data is gone from backups within 30 days.
3. `backup/run.sh:25` (propagation) Each nightly dump is a full pg_dump of the production database (sessions and verification data excluded) uploaded to the bucket, so it contains the live user data of every account at that time.
4. `scripts/backup-cloud-run.sh:34` (propagation) gcloud storage buckets create sets only uniform access and public access prevention. It does not set --soft-delete-duration=0, so the platform default soft-delete window applies.
5. `scripts/backup-cloud-run.sh:38` (sink) The only expiry control is a Delete lifecycle rule with condition age=30 (built at line 37). Objects it deletes enter the soft-delete state and remain restorable for the soft-delete window, past the 30 days promised.
- **Verified evidence:**
  - `scripts/backup-cloud-run.sh:37` Lifecycle JSON contains a single Delete rule with age RETENTION_DAYS (30). No soft-delete, versioning, or retention-policy setting appears anywhere in the script (confirmed by grep for soft_delete/soft-delete across the repository: no hits in scripts/ or backup/).
  - `server/legal.test.ts:12` The policy-versus-system test asserts only that RETENTION_DAYS equals 30 and that the policy text says 30 days. It does not check bucket soft-delete, so the gap is untested.
  - `public/privacy.html:94` The retention row promises that erased data is gone from backups within 30 days, a firm outer bound that a 7-day soft-delete tail would exceed.
  - `scripts/backup-cloud-run.sh:41` The backup service account holds only roles/storage.objectCreator, so the extra recoverable copies are reachable only by privileged project operators, not by the app or other users. This bounds impact to low.
- **Blockers:**
  - The live bucket's soft_delete_policy (retentionDurationSeconds) cannot be observed from source. It may be the 7-day default, 0 if set out of band, or overridden by a project or organization default.
  - Whether the bucket was created before or after the platform change that made soft delete the default for new buckets is unknown.
- **Bounded local plan:** No local reproduction is possible: this is Cloud Storage behaviour. Source review confirms nothing in the repository disables or sets the soft-delete duration.
- **Owner-observed deployment check:** Project owner runs the read-only command `gcloud storage buckets describe gs://$BUCKET --format='value(soft_delete_policy)'` and checks for retentionDurationSeconds greater than 0. If it is non-zero, either run `gcloud storage buckets update gs://$BUCKET --clear-soft-delete` and add `--soft-delete-duration=0` to the create call in cmd_setup, or change the policy and DeleteMyData.tsx wording to 'within 37 days'. Optionally list soft-deleted objects with `gcloud storage ls --soft-deleted gs://$BUCKET` to see the tail. No data is modified by the check.

## 3. import-legacy runs up to 20,000 commands in one transaction on one pooled DB connection with no timeouts, so a few concurrent requests from one signed-in account can exhaust the 10-connection pool

- **Fingerprint:** `import-legacy-20k-command-single-transaction-pins-shared-pool-connection`
- **Claimed root cause:** The import is one unbounded-duration transaction on a shared, small, timeout-less pg pool, and the limiters count it as one request unit regardless of its cost or concurrency. There is no per-user in-flight cap, no statement or lock timeout, and no pool connectionTimeout.
- **Description:** POST /api/commands/import-legacy takes a body of up to 4 MB with up to 20,000 commands. Each command runs the real handler, several queries each, one after another, inside one inUserTransaction. That transaction holds one connection of a default pg.Pool (max 10, no connectionTimeout, statement_timeout or idle_in_transaction timeout configured in source). The same pool serves sessionAuth's ensure_user query on every /api request. The per-user import limiter allows 10 requests per hour, and concurrent requests are not limited. All of them check out a connection; the ones queued behind the first block on lockUser's `select ... for update` while still holding their connection. Ten parallel imports from one account can therefore hold the whole pool for as long as the first import runs. Other users' requests then wait indefinitely for a connection (no pool connectionTimeout), including sign-in lookups and /api/health/db. Making the last command invalid rolls the import back, so the account stays empty and can repeat in the next window. The source path is confirmed. How long a 20k-command import runs, and whether the deployed pooled Neon URL or role sets timeouts, cannot be observed from source. Postgres is unavailable in the sandbox, so I did not reproduce it.
- **Source trace:**
1. `server/app.ts:139` (entrypoint) Authenticated route; calls importLegacy with req.body. Any signed-in Google account (or dev header in dev/test) reaches it.
2. `server/app.ts:90` (propagation) express.json limit raised to 4mb for this route only.
3. `server/app.ts:122` (propagation) importLegacy limiter is 10 per hour per user (LIMITS at line 53) and counts requests, not concurrency or work done. The /api/commands limiter (600/min) also counts it as one unit.
4. `server/commands/importLegacy.ts:50` (propagation) Accepts 1 to MAX_IMPORT_COMMANDS (20,000) commands whose names are in HANDLERS.
5. `server/commands/importLegacy.ts:79` (propagation) lockUser does `select 1 from users ... for update` (support.ts:58-60); concurrent imports for the same user queue here while holding a pooled connection.
6. `server/commands/importLegacy.ts:82` (propagation) Sequentially awaits each real handler inside one transaction on one pooled connection, with no time or work bound beyond the 20k count.
7. `server/db/connection.ts:11` (propagation) new pg.Pool({connectionString, types}) with default max 10 and no connectionTimeoutMillis, statement_timeout or idle_in_transaction_session_timeout.
8. `server/auth.ts:33` (sink) Every authenticated request needs a pool connection for ensure_user, so pool exhaustion blocks all users.
- **Verified evidence:**
  - `server/commands/importLegacy.ts:37` MAX_IMPORT_COMMANDS = 20_000, described as 'a mistake cannot become a flood'; there is no time budget.
  - `server/commands/importLegacy.ts:80` The non-empty check happens inside the transaction. A run that aborts on its last command rolls back and leaves the account empty, so it is repeatable.
  - `server/commands/importLegacy.ts:96` After an Abort, the refusal is written in a second transaction (another connection checkout).
  - `server/app.ts:53` importLegacy limit is max 10 per 60 min per user via byUser (rateLimit.ts:21-40 is a plain request counter with no in-flight tracking).
  - `server/db/connection.ts:11` No pool max, connectionTimeoutMillis or statement timeout is set in source.
  - `scripts/deploy-cloud-run.sh:10` Deploys with max-instances=1, so one instance and one 10-connection pool serve all users. The APP_DATABASE_URL is the pooled Neon URL, whose options (statement_timeout, role settings) are not in the repo.
  - `server/commands/bodyWeight.ts:36` Handlers call lockUser again and run several queries per command, so 20k commands means roughly 100k round trips.
- **Blockers:**
  - Import wall-clock time for a 20,000-command payload against the deployed Cloud Run to Neon pooled path is unknown. Per-query latency decides whether the pool is held for seconds or minutes.
  - The deployed APP_DATABASE_URL, role or database may set statement_timeout, lock_timeout or idle_in_transaction_session_timeout (outside the repo), which would bound or kill the held connections.
  - Local reproduction needs Postgres with the migrations applied; the sandbox has no network or database, so no run was possible.
  - Whether sign-up is open to arbitrary Google accounts (it determines the attacker population). Source shows only that any valid Better Auth session passes sessionAuth.
- **Bounded local plan:** On a scratch local Postgres with migrations applied, using a dedicated test user and the dev header: build a 20,000-command payload of valid log-body-weight (or other cheap create) commands with distinct keys and an invalid last command. Time one import. Then start the app with a small pool, send 10 concurrent import requests as one test user, and measure latency of GET /api/health/db and /api/me from a second user while they run. Record whether it hangs or returns 503, and the pg_stat_activity states (idle in transaction, waiting on the users row lock). Touch no deployed service.
- **Owner-observed deployment check:** Owner-observed and non-destructive: on a staging or throwaway Neon branch with the same role and pooled URL, run the same timing with one import only. Check `SHOW statement_timeout`, `SHOW lock_timeout` and `SHOW idle_in_transaction_session_timeout` for the ironlog_app role. Do not run concurrent imports on the production database. Fix direction: cap in-flight imports per user (and globally) with a mutex or semaphore before taking a connection; set pool max, connectionTimeoutMillis, statement_timeout and lock_timeout; and chunk the import or bound it by time.

## 4. Signed-in user can grow shared Postgres storage without a byte, row or retention cap

- **Fingerprint:** `per-user-unbounded-storage-row-history-refused-writes-no-retention`
- **Claimed root cause:** Abuse control is request-rate only. The schema and commands have no per-user quota on rows or bytes, and no retention job for row_history or refused_writes. The history trigger copies the full row on every update, and the refusal path persists attacker-sized payloads.
- **Description:** The per-user limit counts requests (600 commands/min). It does not count bytes or rows. Three paths let one signed-in Google account add unbounded data. First, every UPDATE on a synced table fires record_row_history, which copies the entire old row into row_history, and nothing prunes that table. Second, each refused write stores up to about 100 KB of payload in refused_writes. A malformed envelope can trigger this with only a session; scrubbed() removes only entry.n, which does nothing for an arbitrary body, so the payload is stored essentially intact. Third, log_entries, library_items and list_items accept unlimited distinct client_ids. At the 600/min limit and up to 100 KB per request, a single account could add on the order of tens of MB per minute. The documented ceiling on the shared Neon database is not observable from source. The hunter's local check confirmed that a 100,868-byte body is kept as a 100,816-byte document. The code shows no per-user storage cap or retention job, and the project backlog lists refused-writes retention as an open decision. The user-facing erase_my_data function does remove a user's own history and refused rows, but an attacker would not call it.
- **Source trace:**
1. `server/app.ts:123` (entrypoint) Any signed-in user may send 600 command requests per minute. The limit is on request count only and nothing limits bytes or stored rows.
2. `server/commands/documents.ts:141` (propagation) An invalid envelope or input calls refuse() and stores the request body in refused_writes. Each successful save of an existing row runs an UPDATE, which fires the history trigger.
3. `src/shared/config.ts:41` (propagation) Config documents of about 100 KB are accepted. The hunter's local check kept 100,816 of 100,868 bytes. Nothing in the code caps the total document size beyond the 100 KB JSON body limit.
4. `server/commands/support.ts:42` (propagation) Inserts the JSON payload into refused_writes with no per-user cap, row cap or retention.
5. `db/migrations/20261007000001_core_tables.sql:70` (propagation) Inserts to_jsonb(old), the full old row, into row_history on every UPDATE. No pruning exists.
6. `db/migrations/20261007000006_library_items.sql:23` (propagation) Unique key is (user_id, client_id) with client_id up to 100 characters. A user can create unlimited distinct keys. The row-history trigger is attached to this table too.
7. `db/migrations/20261008000003_erase_and_delete_account.sql:17` (sink) The only deletion path is the user's own erase function, which uses SECURITY DEFINER. Nothing prunes data automatically.
- **Verified evidence:**
  - `server/app.ts:51` Per-user limits are request counts only: commands 600 per 60,000 ms, sync 120 per minute, importLegacy 10 per hour.
  - `server/app.ts:91` JSON body limit is 100 KB (line 90 sets 4 MB for import-legacy). This sets the per-request size, and there is no cumulative limit.
  - `server/commands/support.ts:32` scrubbed() only removes the entry.n note field. The bad-envelope branch passes the raw body and the other branches pass the envelope input, so large payloads are persisted.
  - `db/migrations/20261007000001_core_tables.sql:70` The trigger copies the whole old row into row_history. The index on replaced_at (line 67) would serve pruning, and no pruning job or code is present.
  - `db/migrations/20261008000003_erase_and_delete_account.sql:32` erase_my_data deletes the user's own row_history and refused_writes (lines 32-33). It is not a retention mechanism.
- **Blockers:**
  - The Neon plan's storage ceiling and quota behavior are not observable from source or the sandbox, and this decides whether growth becomes an outage, a cost spike or a throttle.
  - Measuring row_history and refused_writes growth needs a live Postgres, and the offline sandbox has none.
  - Sign-in is open to any Google account, as the architecture indicates. The production registration policy cannot be verified from source.
- **Bounded local plan:** On a scratch Postgres with the migrations applied, create one dummy user. Save a roughly 100 KB config document 100 times and send 100 invalid envelopes. Then compare pg_total_relation_size for row_history and refused_writes before and after, and extrapolate to 600 requests per minute.
- **Owner-observed deployment check:** The owner should check the Neon project's storage limit and alerting. They should also check whether sign-up is restricted to an allowlist, and whether a periodic prune of row_history and refused_writes by replaced_at / received_at exists outside the repo.

## 5. In-memory rate limiter sweeps its whole map on every request once more than 10,000 live per-IP keys exist, and a rotating IPv6 source gets a fresh bucket each time

- **Fingerprint:** `ratelimit-map-unbounded-fresh-keys-full-scan`
- **Claimed root cause:** server/rateLimit.ts sweeps expired windows only when windows.size exceeds 10_000. It never evicts live keys and has no size cap. It keys on the raw req.ip, so IPv6 addresses are not grouped into /64 prefixes. Many fresh live keys therefore make every request do an O(n) scan, and let a client with many source addresses bypass the per-address limit.
- **Description:** rateLimit() keeps one Map entry per client address, and it only removes entries whose window has expired. Once the map holds more than 10,000 entries, every request walks the entire map. If none of the entries have expired, that walk is pure overhead. The key is the full req.ip, so a caller with a routable IPv6 prefix can create a new entry on every request. Expired entries are only deleted by the sweep, so as long as the attacker keeps adding fresh keys inside one 60-second window the map stays large and every request, legitimate or not, pays the full-map scan on the single Node event loop. The hunter measured about 238us per request at 20k keys, about 1.25ms at 60k and about 1.8ms at 120k, against about 0.5us below the threshold. I did not re-run those timings. The map code and the threshold are visible in source, so the cost model is plausible. The same fresh-address behaviour also means the per-address limits never trigger, including the 10 per minute sign-in limit (server/app.ts:83). Two facts decide whether this is a real availability problem and I cannot see either from source: whether the deployed Cloud Run service accepts IPv6 clients (or lets an attacker get 10k or more distinct source addresses), and what X-Forwarded-For value Cloud Run's front end exposes to Express with trust proxy set to 1. The amplification is also modest. A normal request costs a few hundred microseconds, and the attacker must send roughly one request per fresh key from many addresses. Cloud Run autoscaling and per-instance maps further dilute the effect. If it holds, the impact is slower responses or event-loop starvation on one instance, plus weaker per-address throttling. It does not give access to data or accounts.
- **Source trace:**
1. `server/app.ts:119` (entrypoint) app.use('/api', rateLimit(limits.api)) runs before sessionAuth, so unauthenticated requests reach the limiter. Auth routes (app.ts:83-84) and /api/client-errors (app.ts:88) use their own per-IP limiters of the same type.
2. `server/rateLimit.ts:18` (propagation) The key is req.ip, the full address with no IPv6 prefix grouping, so one routable /64 yields effectively unlimited distinct keys.
3. `server/index.ts:43` (propagation) On Cloud Run (K_SERVICE set) trust proxy is 1, so req.ip is taken from the proxy-supplied X-Forwarded-For. This is the dependency on the deployed front end that I could not check.
4. `server/rateLimit.ts:26` (sink) When windows.size is above 10_000, every request iterates the whole Map. Only expired entries are removed, so when all keys are inside the window the scan is full cost every time and the map never shrinks.
- **Verified evidence:**
  - `server/rateLimit.ts:26` Sweep condition and body: the full-map for loop, and deletion only of entries where t - w.start >= windowMs. Live entries are never evicted and there is no cap.
  - `server/rateLimit.ts:28` A new Window is created for any unseen key at lines 28-32, so each distinct address adds one entry per limiter instance.
  - `server/app.ts:44` AUTH_LIMITS: sign-in is 10 per 60s and other auth routes 120 per 60s. The api limiter is 1200 per 60s (app.ts:50). These per-address ceilings do not apply to a fresh address.
  - `server/index.ts:43` trustProxy is 1 when K_SERVICE is set, so the client address comes from X-Forwarded-For as seen by the Cloud Run front end.
  - `server/rateLimit.test.ts:20` The existing tests do not cover the map-size or sweep-cost behaviour.
- **Blockers:**
  - Whether the deployed Cloud Run URL accepts IPv6 clients, or whether an attacker can otherwise present more than 10,000 distinct req.ip values within one 60-second window. This is deployment and network routing, not visible in source.
  - What X-Forwarded-For the Cloud Run front end passes to the container, and whether an attacker-supplied value can end up as the last entry that Express trusts with trust proxy set to 1.
  - How much the measured scan cost (about 1.25ms per request at 60k keys) slows real traffic on a deployed instance, given its concurrency setting and autoscaling. The cost is per instance and the map is per process.
- **Bounded local plan:** Start the real createApp with trustProxy set to 1 and a stubbed database, and use the existing server/rateLimit.test.ts pattern. Send requests with distinct X-Forwarded-For IPv6 values (2001:db8::N, N from 1 to 60000) in one fixed window, and record request latency before and after the map passes 10k keys. Confirm that sign-in requests from distinct addresses are never 429 while a repeated address is limited after 10 calls. Run it against a local instance only, with a small request count, no external network and no Postgres.
- **Owner-observed deployment check:** The deployment owner checks the Cloud Run service's IPv6 reachability (for example whether the run.app hostname has AAAA records) and uses a harmless header-echo endpoint on a staging copy to see which X-Forwarded-For value the container receives. If either fact fails, close the finding. If both hold, cap the map size (for example evict the oldest entries when it exceeds a fixed bound) and key IPv6 addresses by /64 prefix.
